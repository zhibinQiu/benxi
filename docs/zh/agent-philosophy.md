# 智能体设计哲学

> **本析-企业级 AI 智能体平台** 的思维模型与决策原则（只写现状）。  
> 通信、Plan-and-Execute、并行 DAG 见 [Agent 架构](agent-architecture.md)。

---

## 为什么要分层？

单一大 Agent 会同时遇到：

- **工具膨胀** — 全量 Schema 塞进上下文，决策退化  
- **上下文污染** — 规划与执行细节互相干扰  
- **领域耦合** — 文档 CRUD、RPA、检索 Schema 混杂易幻觉  

对策：**调度只编排，专精管领域，子智能体管步骤，Skill 管固化路径。**

---

## 四类能力（由细到粗）

| 实体 | 一句话 | 谁决策 |
|------|--------|--------|
| **Tool** | 一步动作（搜、查、点、写） | 调用方 LLM |
| **Skill** | 固化的动作组合 + 元数据 | 父层选型，脚本按约定跑 |
| **子智能体** | 隔离上下文的多轮 tool loop | **自己的** LLM |
| **专精 Agent** | 某业务域的完整对话循环 | **自己的** LLM，面向用户 |

```
用户目标
  │
  ▼
调度：意图 → 委托谁？ → 验收汇总
  ├── 常识 / Mermaid 图 → 直接答
  ├── 检索 / 浏览器步骤 / 跑 Skill → 子智能体
  └── 文档 / 报告 / 技能开发 / 双碳 / 电力 / 股市 → 专精
```

**Skill vs 子智能体**：只跑预设路径 → Skill；需要多步推理与自主改计划 → 子智能体。

**专精 vs 子智能体**：专精面向用户、可交终稿；子智能体只交**材料**，终稿由父层写。

## 调度的思维（小析）

1. **完成优先** — 以办成用户事为唯一标准。  
2. **先委托再开口** — 需要检索/执行时，第一轮就调工具入口，禁止空话「我来查一下」。  
3. **不直执原子工具** — 只见编排入口；执行交给子层或专精。  
4. **验收基于真实结果** — 禁止编造；失败如实报告，不擅自改做无关替代服务。  
5. **业务偏好在 MD** — `agent_md/routing/agents.md` 是专精分配的唯一偏好源。

委托速查：

| 意图 | 去向 |
|------|------|
| 常识问答、Mermaid 画图 | 调度直接答 |
| 联网/多源调研 | `kind=search` |
| 已挂载 Skill | `kind=use` |
| 明确步骤（浏览器等） | `kind=execute` + steps |
| 文档/待办/通知/用户 | `platform` |
| 长报告 | `report` |
| 创建/改 Skill | `skill-dev` |
| 碳价/双碳专业 | `carbon` |
| 电力经济 | `power-economy` |
| 个股深度 | `stock` |

## 决策矩阵

```
这是整个对话的目的吗？
  是且属领域操作 → 专精
  是但属检索/通用执行 → 调度委托子智能体
这是父 Agent 流程中的子步骤吗？
  是 → 子智能体（或 Skill）
  否且一步能做 → 原子 Tool（在专精/子层内）
```

**无必要勿增实体**：能原子工具搞定的不启子智能体；能子智能体搞定的不新开专精；能不改编排路由就不加专精。

新增专精成本高（profile + 路由 MD + 状态）；新增子智能体 kind 成本低（配置一行）。

## Loop 与 Plan-and-Execute

对外阶段：`thinking → planning → executing`（可多轮）。  
单 Agent 内再跑六相：输入 → 组装简报 → 推理 → 行动 → 观测 → 更新状态。

System prompt 宜短：放**工作契约**；目标、计划、观测放进每轮动态上下文。  
终稿只引用证据事实，不把工具日志复述给用户。

多智能体时：无依赖可 **parallel**；有先后用 **sequential**（带 prior_handoffs）；复杂依赖用 **TaskDAG** 波次调度。智能体间用 **AIP** 消息与 handoff 通信，不用共享巨型上下文硬塞。

---

## 语言与诚信

- 智能体间消息、注入 LLM 的 system/tool 描述：**英文**  
- 对用户最终回复：跟随用户语言  
- 禁止在面向用户的正文中出现「ROUTE」字样  
- 禁止未调用工具却假装「正在搜索」；禁止编造执行结果
